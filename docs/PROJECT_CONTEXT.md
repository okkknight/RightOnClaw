# RightOnClaw Project Context

## What This Project Is

RightOnClaw is a local macOS AI action layer. It captures user context from macOS entry points, normalizes that context into a shared request model, sends the request to a local bridge, and returns results in native macOS UI.

The current product center is:

- `Select / Capture -> Ask Claw`
- Finder and text Services as broad-coverage entry points
- Finder Sync as a Finder-only enhancement layer
- screenshot capture as a separate capture flow
- a single-window AskPanel for `ask_claw`

RightOnClaw is now **OpenClaw-first, but not OpenClaw-only**. The bridge owns backend discovery and selection and can route to:

- `openclaw`
- `openai_compatible`

The macOS layer stays thin. It owns entry points, selection capture, AskPanel/setup UI, screenshot capture, and bridge calls. It does not own backend orchestration or runtime execution.

## Current Product Surface

### Entry points

- Finder Service: file / folder / multi-path selection
- Text Service: app text selection where macOS `NSServices` is supported
- Finder Quick Action workflow: Finder-only `Ask Claw` workflow bundle
- Finder Sync enhancement layer PoC: Finder toolbar + contextual menu `Ask Claw`
- Menu bar + hotkeys
- Screenshot capture flow

### Current user-facing actions

- `ask_claw`
- `summarize`
- `explain`
- `rewrite`
- `send_to_claw`

### Current UI surfaces

- `AskPanel`: single-window command/conversation surface for `ask_claw`
- `Popup`: non-ask action result popup
- `StreamingPopup`: streaming popup for summarize/explain direct flows
- `SetupPanel`: backend setup/settings entry
- `HUD`: compact loading overlay
- `MenuBar`: menu bar app + hotkey host

## Current Architecture Shape

At a high level:

```text
macOS entry
  -> workflow-cli
  -> workflow-runner
  -> selection / selection_context normalization
  -> AskPanel or direct action delivery flow
  -> bridge-client (localhost HTTP)
  -> bridge-server
  -> ActionRuntime
  -> routers
  -> executor
  -> result stream / result payload
  -> native macOS UI
```

### Layer ownership

- `apps/macos-integration`
  - macOS entry mechanisms
  - workflow generation / installation
  - selection capture
  - screenshot capture
  - AskPanel / popup / setup UI
  - bridge HTTP client
- `apps/bridge-server`
  - local HTTP API under `/v1`
  - config and backend composition root
  - request validation / normalization
  - runtime wiring
- `packages/action-runtime`
  - action definition resolution
  - backend-aware routing
  - object-aware routing
  - public text fast-path routing
  - executor dispatch
- `packages/core`
  - config
  - errors
  - backend config/types
  - shared response helpers
- `packages/credential-layer`
  - credential provider registry
  - shared/configured API-key providers
- `packages/openclaw-client`
  - OpenClaw client contract
  - OpenClaw probe/discovery helpers

## Current Ask Claw Flow

`ask_claw` is the most important path and now uses a dedicated AskPanel session instead of the old ask -> popup -> stream-popup flow.

Key files:

- [apps/macos-integration/src/workflow-cli.ts](../apps/macos-integration/src/workflow-cli.ts)
- [apps/macos-integration/src/workflow-runner.ts](../apps/macos-integration/src/workflow-runner.ts)
- [apps/macos-integration/src/ask-claw-ui.ts](../apps/macos-integration/src/ask-claw-ui.ts)
- [apps/macos-integration/swift/RightOnClawAskPanel.swift](../apps/macos-integration/swift/RightOnClawAskPanel.swift)
- [apps/macos-integration/swift/RightOnClawConversationUI.swift](../apps/macos-integration/swift/RightOnClawConversationUI.swift)

Current behavior:

- selection is normalized first
- AskPanel is launched as a native helper subprocess
- user submits prompt in AskPanel
- workflow-runner streams response from bridge into the same window
- follow-up turns are carried by macOS-side conversation-aware prompt building

The old popup / stream-popup binaries still exist for non-Ask flows, but `ask_claw` no longer depends on them.

## Current Backend Model

The backend layer now lives above executors and is owned by the bridge.

User-facing backends:

- `openclaw`
- `openai_compatible`

Internal execution strategies remain:

- `openclaw`
- `openclaw_responses`
- `model`

Current bridge-side backend files:

- [apps/bridge-server/src/backends/discovery.ts](../apps/bridge-server/src/backends/discovery.ts)
- [apps/bridge-server/src/backends/selection.ts](../apps/bridge-server/src/backends/selection.ts)

- [apps/bridge-server/src/backends/plugins/openai-compatible-plugin.ts](../apps/bridge-server/src/backends/plugins/openai-compatible-plugin.ts)

## Current Stability Boundaries

These layers are already the main stable spine and should be treated as existing system boundaries:

- `workflow-cli -> workflow-runner`
- `selection -> selection_context`
- AskPanel session protocol
- `bridge-client -> bridge-server`
- `ActionRuntime -> routers -> executors`
- backend selection owned by bridge

## Current Known Boundaries

RightOnClaw currently has broad entry coverage, but different entry mechanisms solve different problems:

- Services remain the broad coverage base for Finder + text
- Finder Sync is a Finder-only enhancement layer
- screenshot is an independent capture flow
- AskPanel is the primary `ask_claw` UI, not a generic result view for every action

This matters because current code intentionally does **not** try to collapse all entry mechanisms into one macOS API.
